# calc-math checklist (CALC)
Covers `src/values/calc.rs` (parse, simplification, `reduce_args`, `to_css`) and the math paths of `src/values/percentage.rs` (`DimensionPercentage::add`/`partial_cmp`), `length.rs` (`Length::add`, range clamping), `number.rs` (`NumericRange`), angle and time calc. Spec: `references/spec/syntax-values.md` §4 (anchor keys in §0).
Top failure modes: unbounded recursion and panics in simplification (#910, #1092, e3c8e12; `unreachable!()` #1044/#1129/#1166/#1312); simplification that is not semantics-preserving (incomparable clamp #836, zero terms, percentage folding, round ties, NaN); calc() unwrapped outside the property's range (#1000).
`[open #N]` / `master FAILS` marks a pre-existing bug: answer FAIL only if head is worse than base, extends it to new inputs, or claims the fix while the probe still fails.

- [CALC-01] (BLOCKER) Simplification terminates for every input: sums of parenthesized sums, repeated identical terms, nested min/max/clamp, unlike units and negative terms neither recurse forever nor overflow the stack, and each recursive step provably shrinks the tree (history #166, #242, #611/#791/#827 fixed by e3c8e12, #626, point fix #832 rejected; master FAILS [open #910/#1092]: `Calc::add` (Sum, Sum) at src/values/calc.rs:955 <-> `Length::add` (Calc, Calc) at src/values/length.rs:710; PR #1245).
  verify: R1 (a stack overflow is SIGSEGV/abort, not a Rust panic); probes calc-math/issues-b0-sum-of-parenthesized-sums-no-crash, calc-math/pr1245-nested-sum-stack-overflow, calc-math/issues-important-deep-calc-no-crash, calc-math/devon-calc-repeated-clamp-no-overflow.
- [CALC-02] (BLOCKER) No `unreachable!()`, `unwrap()` or `expect()` on a calc result is reachable from CSS: every math function in every slot type (number, percentage, number-or-percentage, alpha, color channel, length, angle, time) parses or returns an error (#1044, #1129, #1166 fixed by #1131 v1.31.0; [#1312] still open on GitHub but fixed on master by #1329: src/values/percentage.rs:39-41 returns InvalidValue).
  verify: R1; probes calc-math/community-prs-sign-percentage-panic, calc-math/issues-b5-percentage-math-no-panic, calc-math/issues-b2-minmax-numbers-in-percentage-slot-no-panic, calc-math/community-prs-clamp-number-args, calc-math/issues-b3-number-math-in-percentage-slot; grep the diff for `unreachable!`/`unwrap()` on parse results.
- [CALC-03] (BLOCKER) A top-level calc() is unwrapped only when its result lies inside the property's literal range; otherwise the result is clamped exactly as computed-value clamping would do (`NonNegative`, #1329) or calc() is kept, and nested math functions never clamp (regression class #1000, fixed for `[0,∞]` by #1329; master FAILS for other ranges: `font-weight:400;font-weight:calc(1001)` -> `font-weight:1001`, which also deletes the 400).
  verify: probes calc-math/ssv-negative-calc-nonnegative, calc-math/issues-b1-negative-calc-clamped, calc-math/issues-important-calc-negative-length-clamped, calc-math/ssv-out-of-range-calc-font-weight; `non_negative_test`/`property_range_test` in the PR on properties whose initial value differs from the clamped result (padding's initial 0 hides the bug).
- [CALC-04] (MAJOR) clamp(), min() and max() reduce only when every comparison is known: incomparable arguments keep the function, MIN wins over MAX in clamp(), and single-argument and `none` forms follow V4#comp-func (ddc9ce8 fixed #836 `clamp(100px, 200px, 1vh)`; INV-CALC-007, INV-CALC-012).
  verify: probes calc-math/devon-clamp-incomparable-max, calc-math/devon-calc-repeated-clamp-no-overflow, calc-math/community-prs-clamp-number-args.
- [CALC-05] (MAJOR) Math containing `var()`, `env()` or unknown functions is never reordered, folded or partially simplified (`calc(var(--x) * 5)` stays as written, cssnano EM-24), and whitespace is dropped only around `*`, `/` and `,` in a grammar-aware path, never around `+`/`-` (INV-CALC-003; #646 doubled whitespace; size regression [open #1378] since 32f1f52).
  verify: mutations var-before, var-after; probe custom-properties/adjacent-var-whitespace-preserved; S2 on the realworld lane (daisyui, basecoat); R2.
- [CALC-06] (MAJOR) Type errors are not repaired into typed values: `calc(0 + 5px)`, `calc(100px - 0)`, `calc(.25 + 25%)` in `opacity` and `calc(5px - 5px + 10s)` stay Unparsed so the earlier valid declaration survives, and typed division (`<dim> / <dim>`) is folded only for absolute same-dimension units (V4#calc-type-checking; master FAILS: Sum(Value, Number) is typed, pinned by src/lib.rs:8538 `calc(1px + 1)`, #928 closed; #1279 asks for typed division).
  verify: probes calc-math/issues-b0-unitless-zero-in-calc-keeps-fallback, calc-math/ssv-typed-division-passthrough, calc-math/ssv-unitless-zero-inside-math; mutation duplicate-nonadjacent.
- [CALC-07] (BLOCKER) Zero-valued terms are not dropped from a Sum unless another term has the same unit: `calc(10px + 0%)` keeps its `0%`, and `calc(100% - 100% + 1px)` computes to `calc(0% + 1px)` (V4#calc-simplification, V4#calc-computed-value; master FAILS: src/values/percentage.rs:404-414 returns the other operand).
  verify: probes calc-math/ssv-zero-percent-term-height, calc-math/arch-props-values-zero-percentage-dropped-from-calc (use `height` with an indefinite basis; `width` diverges in engines, csswg #10969).
- [CALC-08] (BLOCKER) Basis-relative values (percentages; em, viewport and container units against px) are never compared or folded at parse time in min/max/clamp/round/mod/rem/hypot/abs/sign, because the basis may be negative or zero; only same-unit or absolute-unit values fold (V4#calc-simplification; master FAILS for min/max/clamp: `Calc::reduce_args` src/values/calc.rs:658-711 and clamp :376-432 compare via src/values/percentage.rs:458-466).
  verify: probes calc-math/ssv-min-percentages-negative-basis, calc-math/ssv-clamp-percentages-negative-basis; O1 on `background-position` with an image larger than the box.
- [CALC-09] (MAJOR) Build-time evaluation reproduces CSS semantics: a top-level NaN becomes 0, ±∞ clamps, `-0` becomes 0, NaN/∞ are never printed as a finite number (`5.10424e38px`), and `round/mod/rem(x, 0)` are NaN (V4#calc-ieee, V4#round-infinities; master FAILS for unrestricted ranges: `margin-left:mod(5px,0px)` -> `5.10424e38px`; NonNegative slots mask it).
  verify: probe calc-math/ssv-mod-zero-step-nan (the `width` probe calc-math/arch-props-values-nan-must-be-censored-to-zero passes on master only through clamping); WPT css/css-values/round-mod-rem-computed.html; output-not-contains `e38`.
- [CALC-10] (MAJOR) round() breaks `nearest` ties toward +∞ and implements `up`/`down`/`to-zero` per V4#typedef-rounding-strategy; mod() takes the sign of B and rem() the sign of A; unimplemented forms (`round(A)`, `round(line-width, …)`) pass through (master FAILS: `f32::round` at src/values/calc.rs:116 turns `round(-2.5px,1px)` into `-3px`; Blink, Gecko and WebKit give -2px).
  verify: probe calc-math/ssv-round-nearest-tie-upward; WPT round-mod-rem-computed.html.
- [CALC-11] (MAJOR) Parse cost stays linear in nesting depth: no new `try_parse` alternatives that re-parse the same nested arguments at every level ([open #1098] `atan2` tries 5 types per level, O(5^depth); unclosed nested `calc(` grows ~x10 per 4 levels (depth 20: 1.5 s), EM-26 `rgb( /` and `hsl(atan2(` UNVERIFIED; only TokenList has a depth guard).
  verify: R1 timeouts; generated depth-18 and depth-22 probes (`expect: no-panic`) timed on base and head; read `try_parse` use in the parse_sum/parse_product/math-function paths of the diff.
- [CALC-12] (MAJOR) Math and numeric functions LightningCSS does not model (`sibling-index()`, `progress()`, `random()`, `calc-size()`, `if()`, `clamp(none, …)`, `round(line-width, …)`, typed arithmetic) pass through verbatim, never evaluated, partially simplified or dropped (INV-V5-001).
  verify: probes calc-math/ssv-sibling-index-passthrough, calc-math/ssv-typed-division-passthrough, custom-properties/ssv-if-passthrough; O7 `pass` where the engine supports the function and `unsupported-input`/`both-unsupported` where it does not, never `computed-difference` or `valid-became-invalid`.
- [CALC-13] (MAJOR) `clamp()` is lowered to exactly `max(MIN, min(VAL, MAX))` only when `ClampFunction` is unsupported, with the same targets in MinifyOptions and PrinterOptions (src/values/calc.rs:163-174), and any new lowering for round/mod/rem/abs/sign/trig is exact and gated on its own compat feature, otherwise the original is kept (none exists today).
  verify: probe calc-math/ssv-clamp-lowering (lower, safari 13); mutations retarget-none, retarget-legacy, wrap-supports; legacy Chromium/Firefox lack round/mod/rem/abs/sign, WebKit 15.4+ has them (O4 shows the unlowered declaration dropped).
- [CALC-14] (MAJOR) A change to a calc-carrying type (`Length`, `DimensionPercentage`, `Angle`, `Time`, `CSSNumber`, `Percentage`) is exercised in every slot that parses through it: color channels and alpha, gradients, transforms, filters, box-shadow, font-size, line-height.
  verify: S1 and radius_areas; O7 over css/css-values and the touched property directories; probe calc-math/issues-b3-number-math-in-percentage-slot.
- [CALC-15] (MINOR) Re-serialized math keeps its value within f32 precision: `Product(n < 1, f)` printed as `f/(1/n)` (src/values/calc.rs:984-990) never divides by `3.40282e38` for `0 * f`, and `e`/`pi`/`exp()` results stay within 6 significant digits (INV-CALC-009, INV-CALC-010).
  verify: `lcr show` text; output-not-contains `e38`.
